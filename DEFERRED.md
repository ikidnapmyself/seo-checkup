# Deferred register

This is the register promised at the end of phase 1 of the 1.0.0 modernization: everything considered and knowingly not built in this release, why it was deferred, and what it would be worth. The agreed next phase is a CLI and a self-contained PHAR.

| Item | Why deferred | Value |
|---|---|---|
| `Dom\HTMLDocument` HTML5 parser (PHP 8.4+) | `DOMDocument` is an HTML4 parser. It flags `<main>`, `<section>`, `<article>` and `<nav>` as invalid tags — currently swallowed by `libxml_use_internal_errors(true)` — and swapping to `Dom\HTMLDocument` would change the output of nearly every check simultaneously. That blast radius is exactly what this phase avoided; the PHP floor was deliberately held at 8.3 rather than 8.4 for this reason. | Highest — the library is currently parsing 2026 markup with a parser that predates the HTML5 elements most sites are built from. |
| GA4 / GTM detection | `googleAnalytics()` matches only the legacy `UA-XXXXX-X` format. `UA-` IDs are effectively dead; detecting `G-` (GA4) and `GTM-` (Tag Manager) is a new check, not a fix to the existing one. | High |
| Public Suffix List for `domainLength()` | `domainLength()` strips only the final label of the host, so `example.co.uk` measures as `example.co` instead of stripping the registrable domain's public suffix (`co.uk`). Correct extraction needs the Public Suffix List, which is a new dependency. Defect 9 in the CHANGELOG fixed the crash on hostless URLs but deliberately left this measurement rule unchanged. | Medium |
| PSR-7 / raw-HTML input source | `Analyze` only ever fetches a live URL. Accepting a pre-fetched PSR-7 response or raw HTML string is a new input surface, not a fix. | Medium |
| Verdicts, severities, budgets | Every check currently returns raw data with no pass/fail judgment, severity, or numeric budget attached. Building that is a new output layer over all 29 checks. | Medium |
| CLI + self-contained PHAR | The agreed next phase after this one. | Medium |
| Docker image, GitHub Action | Downstream of the CLI; blocked on it existing first. | Low |
| Wider 2026 SEO catalogue | Structured data / JSON-LD, Core Web Vitals, hreflang, sitemap validation and similar are new checks, out of scope for a polish-only release. | Low |
| AI/LLM analysis layer | An entirely new subsystem layered on top of the raw check output. | Low |
| The `999` carve-out in `brokenLinks()` is unreachable in production | `brokenLinks()` treats HTTP `999` (LinkedIn's non-standard bot-block response) as passed rather than an error via `$status !== 999`. But `GuzzleHttp\Psr7\Response` rejects status codes outside 100–599, so a real `999` response never reaches that comparison — it becomes a transport failure instead, `Fetcher::status()` returns `0`, and the link is bucketed as `"HTTP 0"` under errors. The carve-out is dead code against Guzzle's default (curl) handler. Discovered during Task 11's defect-10 fix; human ruling on 2026-08-13 was to log it and move on rather than rework the fetch layer for one non-standard status code. | Low — cosmetic bucketing of an edge case that already lands in "errors" either way. |
| `codeContent()`'s size fields can contradict each other on very small bodies | `Document::text()` appends a trailing space per text node it visits. On a body small enough that this padding outweighs the content, `content_size` can exceed `page_size`: a 1-byte body (`"x"`) yields `page_size => 1`, `code_size => 0` (clamped by `max(0, ...)`), `content_size => 2`, `percentage => "200%"`. Confirmed by direct execution during Task 12. The honest fix is in `Document::text()`'s per-node spacing, not in `codeContent()` itself, and was deferred rather than reworking a shared, widely-depended-on method late in the release. | Low — confined to bodies under roughly five bytes; no real page triggers it. |
| PHPStan `max` | The project is clean at `level: 8`; raising to `level: max` reports errors in `tests/` only. When this was first measured (2026-08-14, Task 16 release verification) there were 67: two genuine precision gaps in production code — `Analyze.php` passing `array<list<string>>` where `PageContext` wants `array<string, list<string>>`, and `SystemDnsLookup::txtRecords()` returning `list<array>` where the interface promises `array<int, array<string, mixed>>` — and 65 in `tests/`. **Both production errors were fixed in the final review wave** by making the types honest (the header map is built key by key, and each DNS record is rebuilt with string keys); no ignores and no baseline were used, and `phpstan.neon.dist` stays at `level: 8`. `level: max` now reports 68 errors, **all of them test-side**: the 65 already registered, plus 3 more of exactly the same kind from the regression tests that same wave added. They are all in `tests/` (`ContentChecksTest.php`, `HeaderChecksTest.php`, `LinkChecksTest.php`, `MetaChecksTest.php`, `MiscChecksTest.php`, `NetworkChecksTest.php`, `AnalyzeEnvelopeTest.php`), all `offsetAccess.nonOffsetAccessible` / `argument.type`, from tests indexing into the check envelope's `data` field — `Output()` returns `data` as `mixed` by design, so every test that reaches into `$result['data'][...]` is untyped at the boundary and PHPStan cannot narrow it. Closing them means giving the envelope a real shape — a typed result object or per-check generics — which is a design change, not a type annotation, and was explicitly out of scope for this phase. | Low — what remains is blocked on the same typed-envelope redesign already listed above under "Verdicts, severities, budgets," so resolving it is naturally sequenced with that work rather than done piecemeal. |
| `Document` assumes the body is UTF-8 | `Document::dom()` runs `mb_encode_numericentity($html, ..., 'UTF-8')` before `DOMDocument::loadHTML()`, which is correct for a UTF-8 page and lossy for anything else: an ISO-8859-1 page loses its non-ASCII text, so `café naïve` reaches every check as `caf? na?ve`. The response's declared charset is already known — `PageContext` holds the headers and `characterSet()` parses it — but `Document` is constructed from the body string alone, so the information does not reach the decode. Threading it through means changing `Document`'s constructor and re-checking output for every check that reads text (`codeContent()`, `plaintextEmail()`, `metaTitle()`, `metaDescription()`, `header1()`, `header2()`, `inlineCss()`, `cache()`), which is exactly the release-wide blast radius this phase avoided. Raised in the final whole-branch review on 2026-08-14 and deliberately deferred there. | Medium — real but confined to non-UTF-8 pages, a shrinking minority of the web; the fix is naturally sequenced with the `Dom\HTMLDocument` parser swap above, which touches the same decode path. |
